# 【立项】BOM选型评审及交付风险预警系统

创建日期：2026-07-10

## 项目名称与一句话简介

项目名称：BOM选型评审及交付风险预警系统

一句话简介：面向研发、采购、质量、项目管理和供应链团队的轻量化BOM风险评审工具，通过导入BOM与供应数据，自动识别物料选型和交付风险，并输出可解释的评审报告。

## 项目背景

当前项目希望同时覆盖两个场景：

1. 新项目设计阶段的BOM选型评审，判断某个物料是否推荐使用。
2. 项目交付或量产准备阶段的供应风险预警，识别交期、库存、停产、替代料等风险。

首版目标不是建设完整的ERP、PLM或供应链协同平台，而是在一周内做出一个能跑通核心逻辑的本地工具。系统先支持BOM Excel导入、自动风险评分和评审报告导出，后续再考虑接口对接、服务器部署、多人权限和通知能力。

## 目标用户

首版系统面向5–20人的小范围团队使用，重点角色包括：

- 研发工程师：提交或导入BOM，查看物料是否适合选型。
- 采购人员：维护或导入价格、交期、供应商来源等信息。
- 供应链计划人员：关注库存变化和交付风险。
- 质量或SQE人员：后续可补充供应商质量风险数据。
- 项目经理：查看BOM整体风险结论，导出评审报告。

首版不做复杂权限区分。系统可先采用简单登录或本地访问控制，重点保证数据可追溯和操作有记录。

## MVP范围

一周内的最小可用版本建议只做三件事：

| 优先级 | 功能 | 说明 |
|---|---|---|
| P0 | BOM导入 | 支持从Excel导入单层BOM，识别物料编码、物料名称、规格、用量、版本、替代料关系、虚拟件标识等字段。 |
| P0 | 自动风险评分 | 按预设规则识别单一来源、价格异常上涨、交期超过阈值、库存下降过快、停产、无替代料等风险，并给出物料级推荐结论。 |
| P0 | 导出评审报告 | 输出Excel或Markdown报告，包含物料风险等级、风险原因、建议动作和BOM整体风险摘要。 |

首版明确不做以下内容：

- 不对接ERP或PLM。
- 不做完整审批流。
- 不做复杂多角色权限。
- 不做实时通知。
- 不做AI预测模型。
- 不做多层BOM展开。

## 核心用户故事

### 用户故事1：导入BOM并识别风险

作为研发工程师，我希望导入一个Excel格式的单层BOM，系统能自动匹配物料主数据和供应风险数据，告诉我哪些物料不建议继续使用。

验收标准：

- 用户可以上传`.xlsx`文件。
- 系统能读取指定Sheet或默认第一个Sheet。
- 系统能校验必要字段是否存在。
- 缺失关键字段时给出明确提示。
- 导入后生成物料级风险结果。

### 用户故事2：查看物料是否推荐使用

作为项目经理，我希望系统给每个物料输出“推荐使用”“谨慎使用”“不推荐使用”的结论，并说明原因。

建议规则：

| 结论 | 判断逻辑 |
|---|---|
| 推荐使用 | 无高风险项，交期、库存、替代料状态正常。 |
| 谨慎使用 | 存在中风险项，例如交期偏长、库存下降较快、价格上涨但仍可控。 |
| 不推荐使用 | 存在高风险项，例如停产、单一来源且无替代料、交期严重超过阈值、库存快速下降。 |

### 用户故事3：导出评审报告

作为项目经理，我希望在评审会议前导出一份报告，用于说明BOM整体风险和需要处理的物料。

报告建议包含：

- 项目或BOM名称
- 导入时间
- 物料总数
- 高/中/低风险物料数量
- 不推荐使用物料列表
- 每个风险物料的风险原因
- 建议动作，例如寻找替代料、确认供应商交期、评估库存安全量、切换非停产物料

### 用户故事4：记录操作日志

作为系统负责人，我希望系统记录导入、评分、导出等操作，方便追溯谁在什么时候处理了哪份BOM。

首版日志字段建议：

| 字段 | 说明 |
|---|---|
| 操作时间 | 记录操作发生时间。 |
| 操作类型 | 导入BOM、执行评分、导出报告、修改规则等。 |
| 操作对象 | 文件名、BOM名称或规则名称。 |
| 操作结果 | 成功、失败、失败原因。 |
| 操作者 | 首版可先记录本机用户名或手工输入的用户名称。 |

## 核心数据对象

### BOM明细

| 字段 | 说明 |
|---|---|
| BOM版本 | 用于区分同一项目的不同BOM版本。 |
| 物料编码 | 物料唯一标识。 |
| 物料名称 | 物料描述。 |
| 规格型号 | 用于辅助识别。 |
| 用量 | 当前BOM中使用数量。 |
| 是否虚拟件 | 标记虚拟件，首版不展开多层结构。 |
| 替代料组 | 标识哪些物料属于可替代关系。 |
| 是否共用料 | 标识多个项目共用的物料。 |

### 供应风险数据

| 字段 | 说明 |
|---|---|
| 物料编码 | 与BOM明细关联。 |
| 供应商数量 | 判断是否单一来源。 |
| 主供应商 | 当前主要供应商。 |
| 标准交期 | 用于判断交期风险。 |
| 当前库存 | 用于判断库存风险。 |
| 库存变化率 | 用于判断库存是否下降过快。 |
| 当前价格 | 用于判断价格变化。 |
| 历史价格 | 用于计算价格涨幅。 |
| 是否停产 | 判断物料生命周期风险。 |
| 是否有替代料 | 判断选型安全性。 |

### 风险规则

| 规则 | 建议首版阈值 | 风险等级 |
|---|---:|---|
| 单一来源且无替代料 | 供应商数量 = 1 且无替代料 | 高 |
| 停产物料 | 是否停产 = 是 | 高 |
| 交期严重超阈值 | 标准交期 > 60天 | 高 |
| 交期偏长 | 标准交期 > 30天且 ≤ 60天 | 中 |
| 价格异常上涨 | 价格涨幅 > 20% | 中 |
| 库存下降过快 | 最近周期库存下降率 > 30% | 中 |
| 无替代料 | 是否有替代料 = 否 | 中 |

这些阈值不应写死在代码里。首版可以放在一个规则配置表或配置文件中，便于后续调整。

## 推荐技术栈

遵循奥卡姆剃刀原则，首版建议选择最少组件、最短路径、最容易维护的方案。

### 前端

推荐：Streamlit内置页面

理由：

- 你目前只安装了Python，没有前端技术偏好。
- Streamlit可以用Python直接写页面，不需要单独学习Vue、React、前端构建工具和接口联调。
- 很适合数据导入、表格展示、筛选、评分结果展示和报告导出。
- 一周内做MVP更稳。

适用页面：

- BOM上传页
- 风险评分结果页
- 风险规则配置页
- 历史记录页
- 报告导出页

### 后端

推荐：Python单体应用

理由：

- 首版功能集中在Excel读取、规则计算、表格展示和文件导出，Python生态成熟。
- 可使用`pandas`处理Excel和评分逻辑。
- 不需要额外引入FastAPI、Django或复杂服务架构。
- 后续如果需要接口化，可把评分逻辑拆出来，再接FastAPI。

建议核心库：

| 库 | 用途 |
|---|---|
| streamlit | 构建本地Web页面。 |
| pandas | 读取Excel、清洗数据、计算风险。 |
| openpyxl | 读写Excel报告。 |
| sqlite3 / SQLAlchemy | 保存数据和日志。 |
| plotly | 可选，用于风险统计图表。 |

### 数据库

推荐：SQLite

理由：

- 本地部署简单，不需要安装数据库服务。
- 足够支持5–20人首版试用。
- 适合保存BOM导入记录、风险评分结果、规则配置和操作日志。
- 后续迁移到PostgreSQL或MySQL的成本可控。

不建议首版直接使用大型数据库，除非公司已有明确标准。当前需求下，数据库服务本身会增加部署和维护成本。

### 部署

首版推荐：本地电脑运行Streamlit

运行方式示例：

```bash
streamlit run app.py
```

后续推荐：公司服务器 + Docker + PostgreSQL

演进路径：

1. 单机Streamlit + SQLite，验证业务规则。
2. 局域网部署Streamlit，少数人访问。
3. 拆分为FastAPI后端 + Vue/React前端或继续保留Streamlit。
4. 数据库迁移到PostgreSQL。
5. 增加统一登录、权限、通知和接口对接。

## 备选技术方案

### 方案A：Streamlit + Python + SQLite

适合首版，推荐采用。

优点：

- 开发最快。
- 技术栈最少。
- 非专业开发团队也较容易理解。
- 非常适合Excel导入、规则计算和报告导出。

风险：

- 不适合长期承载复杂权限和高并发。
- 页面交互能力弱于专业前端框架。
- 多人同时使用时需要谨慎处理文件上传和数据库写入。

### 方案B：FastAPI + Vue + PostgreSQL

适合正式产品化阶段。

优点：

- 前后端边界清晰。
- 后续对接ERP、PLM、统一登录更方便。
- 更适合多人协作、权限管理和接口扩展。

风险：

- 一周内交付压力大。
- 需要前端、后端、数据库和部署知识。
- 对当前团队来说学习成本偏高。

### 方案C：Excel模板 + Python脚本

适合极简验证规则。

优点：

- 最快验证评分规则。
- 几乎不需要页面开发。
- 对现有Excel流程影响最小。

风险：

- 不像一个系统。
- 操作日志、历史版本、多人使用体验较弱。
- 后续扩展成平台时需要重做交互层。

### 方案D：低代码平台

适合公司已有低代码平台的情况。

优点：

- 表单、权限、审批可能更快。
- 对业务人员更友好。

风险：

- Excel解析、复杂规则评分、报告导出可能受平台限制。
- 后续迁移和二次开发能力取决于平台。
- 如果公司没有现成平台，首版不建议为此引入。

## 技术栈合理性评估

你当前没有明确技术栈，只安装了Python。因此推荐方案与当前能力匹配度较高。

### 强项

- Python适合处理Excel和表格数据。
- Streamlit降低了前端开发门槛。
- SQLite降低了数据库部署门槛。
- 单体应用适合一周内做出可演示版本。
- 规则评分逻辑容易解释，也方便业务人员调整。

### 风险

- Streamlit不是传统企业级后台框架，复杂权限、复杂流程和高并发不是它的强项。
- SQLite适合首版，不适合多人高频并发写入。
- 如果后续要接ERP/PLM，需要重新设计接口层。
- 如果风险规则持续变复杂，需要把规则配置做成可维护结构，避免散落在代码里。

### 结论

首版建议选择“Streamlit + Python + SQLite”。它不是终局架构，但非常适合当前阶段：需求仍在验证、团队技术储备偏Python、本地部署、5–20人试用、一周内出成果。

## 关键设计决策记录

### 决策1：首版做工具，不做流程平台

原因：当前最紧迫的价值是判断物料是否推荐使用，并输出可解释的风险报告。审批流、多人权限和通知能力会增加大量边界条件，不利于一周内交付。

结论：首版只做BOM导入、风险评分、结果查看和报告导出。

### 决策2：使用规则评分，不使用AI预测模型

原因：当前风险判断维度明确，包括单一来源、价格上涨、交期超阈值、库存下降过快、停产和替代料状态。规则模型更容易解释，也更容易被业务人员接受。

结论：首版采用规则引擎式评分，每个风险结论必须能展示触发原因。

### 决策3：选择SQLite作为首版数据库

原因：本地部署和一周交付要求下，SQLite无需安装数据库服务，能满足导入记录、评分结果、规则配置和操作日志的存储需求。

结论：首版使用SQLite；当系统迁移到公司服务器并出现多人并发写入需求时，再迁移到PostgreSQL。

### 决策4：暂不对接ERP或PLM

原因：ERP/PLM对接通常涉及接口权限、字段映射、数据质量、网络访问和验收流程。首版目标是验证风险评分逻辑，不应把集成工作放在第一阶段。

结论：首版通过Excel导入BOM，通过接口或表格导入供应数据，但不做系统级实时对接。

### 决策5：必须保留操作日志

原因：BOM评审和风险结论会影响物料选型与交付判断，需要知道数据何时导入、规则何时执行、报告何时导出。

结论：首版记录导入、评分、导出和规则修改日志。

### 决策6：支持替代料、共用料、虚拟件和版本差异，但不做多层展开

原因：这些字段会直接影响风险判断，但多层BOM展开会明显增加复杂度。当前需求明确为单层BOM，因此先保留字段和标识，不引入层级展开逻辑。

结论：首版在数据模型中保留相关字段，评分时使用这些字段；多层BOM留到后续版本。

## 首版页面建议

## 最终建议

首版不要从“供应链风险监控平台”的完整形态开始做，而要从“BOM导入 + 规则评分 + 可解释报告导出”的闭环开始。这个闭环能最快验证业务价值，也能沉淀后续系统化所需的数据结构、风险规则和评审口径。

推荐首版技术栈：

| 层级 | 推荐方案 |
|---|---|
| 前端 | Streamlit |
| 后端 | Python单体应用 |
| 数据库 | SQLite |
| Excel处理 | pandas + openpyxl |
| 部署 | 本地运行，后续迁移到公司服务器 |

这套方案的核心价值是简单、稳定、少依赖，符合一周内立项并启动Vibe Coding的目标。
