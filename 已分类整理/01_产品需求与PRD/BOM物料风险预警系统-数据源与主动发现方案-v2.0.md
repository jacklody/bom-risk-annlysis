## 1. 数据源全景 · 九大类渠道

系统不再局限于少数几个 API，而是建立多维情报网，确保覆盖面、真实性和时效性。

### 1.2 分级调用策略

这些数据源不是同一时间全部调用，而是按系统场景分级启动：

**T1 实时级** — BOM 上传/手动触发分析时：

```text
并发调用：
├─ LCSC jlcsearch API       ← 库存 + 价格
├─ Mouser API               ← 库存 + 交期 + 生命周期
├─ 半导小芯/芯查查            ← 生命周期 + 替代推荐
└─ 云汉芯城                  ← 国产替代 + SPU标准化
```

**T2 日常巡检级** — 定时任务自动运行：

```text
轮询执行：
├─ DigiKey API              ← 每周价格 + 库存快照
├─ 华秋                      ← 每日价格快照
├─ 原厂官网公告              ← 每日爬取
├─ 企查查/天眼查             ← 每周供应商风险
├─ 行业媒体 RSS              ← 每日汇总
└─ KOL/大V监听               ← 每日汇总
```

**T3 事件驱动级** — 收到推送/邮件/关键词触发：

```text
邮箱收到供应商通知  → 立即解析并结构化
媒体出现涨价/停产关键词 → 立即进入待确认事件队列
价格快照出现 > 10% 波动 → 生成趋势风险事件
企查查返回供应商经营异常 → 标记该供应商所有物料
```

## 2. 置信度分流 · 取代全员人工确认

v1.1 的流程要求所有事件进入人工确认。这是不现实的——每天若涌入数十条供应商公告、行业新闻、价格波动，全靠人工确认将失去时效性。

v2.0 引入**置信度自动分流**机制。

### 2.1 置信度模型

每条事件的结构化抽取结果都会附带一个置信度评分（0–100）和各维度可信度。

事件置信度由四个维度合成：

| 维度 | 权重 | 得分逻辑 |
|------|:---:|------|
| **来源权威性** | 30% | 原厂官网100 → API返回95 → 媒体80 → 用户上传70 → KOL50 → 匿名/web抓取30 |
| **字段完整度** | 35% | 厂商+品类+涨幅+生效日全有→100；缺1→70；缺2→40；信息不足→20 |
| **抽取值信度** | 20% | 精确正则匹配→100；模糊匹配→70；LLM推断→60；无匹配→0 |
| **多渠道交叉验证** | 15% | 同一事件≥3个独立来源确认→100；2源→80；单源→50；无法验证→30 |

### 2.2 三级分流

```text
                    ┌─────────────────────────┐
                    │    事件结构化抽取          │
                    │   + 自动计算置信度(0-100) │
                    └────────────┬────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ↓                  ↓                  ↓
        置信度 ≥ 80           置信度 50-79        置信度 < 50
     「自动确认」            「待人工确认」        「仅记录」
              │                  │                  │
              ↓                  ↓                  ↓
    ┌─────────────────┐  ┌──────────────┐  ┌──────────────┐
    │ 直接生效         │  │ 推送确认任务   │  │ 存入待补充区   │
    │ 触发定时/实时分析 │  │ 1小时内未处理  │  │ 不触发业务动作  │
    │ 写入事件库        │  │ →自动降级处理  │  │ 等待更多信息    │
    └─────────────────┘  └──────────────┘  └──────────────┘
```

### 2.3 各类事件的典型置信度和处理方式

| 事件来源示例 | 典型置信度 | 默认处理 |
|-------------|:---:|------|
| Mouser API返回 EOL 状态 | 95 | 自动确认，直接红色 |
| 原厂官网公告涨价 + 涨幅 + 日期 | 90 | 自动确认，触发全量BOM分析 |
| 三个独立媒体同时报道同一厂商涨价 | 85 | 自动确认 |
| 云汉芯城API返回NRND | 85 | 自动确认 |
| 用户上传供应函扫描件且OCR清晰 | 75 | 待人工确认 |
| 邮件正文涨价通知且抽取完整 | 75 | 待人工确认 |
| 单家媒体提到某品类可能有调价趋势 | 55 | 仅记录，不触发分析 |
| 群聊天截图模糊，OCR部分识别失败 | 30 | 仅记录 |
| Tweet/朋友圈提到"听说XX要涨价" | 20 | 仅记录，等待验证 |

### 2.4 待人工确认的超时降级

待确认队列设 1 小时超时。若 1 小时内无人确认：

```text
置信度 70-79 → 自动确认，黄色风险（低于≥80的红色/橙色）
置信度 60-69 → 自动确认，仅标记为"关注"，绿色
置信度 50-59 → 自动归档，不触发BOM分析，保留备查
```

### 2.5 人工确认页面展示

系统不要求用户逐个字段填空，而是把解析结果亮给用户，用户只需：

1. 一眼看清解析出的：厂商 × 品类 × 涨幅 × 生效日 × 原因。
2. 每个字段右侧有置信度徽标（绿色高/黄色中/红色低）。
3. 一键「确认」。
4. 也可点击单字段修正后「确认」。

这样每天十几条事件，只需处理那些系统拿不准的 2-3 条。

## 3. 主动实时风险发现引擎

v1.1 的流程偏向"事件驱动"——等人上传或等新闻出现。v2.0 增加**主动发现层**，让系统自己去找风险。

│  │                 │  │                 │  │                 │ │

### 3.2 三哨兵详解

**价格哨兵**：

每天拉取所有活跃BOM中物料的当前价格，与前一次快照对比。触发条件：

```text
单物料价格波动 ≥ 10%  →  生成 price_trend 事件
同一品牌 ≥ 5 颗物料同期上涨 ≥ 5%  →  综合为品牌涨价事件
同一品类 ≥ 10 颗物料（跨品牌）同期上涨  →  行业性涨价信号
```

**库存哨兵**：

每天拉取库存数据，与快照对比。触发条件：

```text
总库存从 > 安全线 跌至 0  →  立即生成 stock_critical 事件
总库存 30 天内下降 > 50%  →  生成 stock_draining 事件
所有渠道均无现货（之前有） →  生成 supply_interruption 事件
```

**生命周期哨兵**：

每周对历史BOM中所有 MPN 重新查询生命周期状态。触发条件：

```text
Active → NRND  →  红色风险（不得再用新设计）
Active → EOL   →  红色风险 + 立即触达项目经理
NRND → EOL     →  红色风险 + 获取 LTB 窗口
首次发现 Last Time Buy 标签 →  红色风险
```

### 3.3 影响量化 pipeline

这是 v2.0 的核心——不再是泛泛的"注意风险"，而是算出对每个项目、每个BOM的实际影响。

**量化链路**（涨分为例）：

```text
涨价事件 (厂商=扬杰, 品类=二极管, 涨幅=10%-20%, 生效日=2026-07-01)
  │
  ├─ 匹配历史BOM → 命中3个项目、42颗物料
  │
  ├─ 【单颗级量化】
  │   └─ 单颗成本增加 = 当前单价 × 涨幅
  │
  ├─ 【单板级量化】
  │   └─ 单板成本增加 = Σ(单颗成本增加 × 单板用量)
  │   └─ 单板成本涨幅 = 单板增加 / 原单板总成本
  │
  ├─ 【批量级量化】
  │   └─ 批次成本增加 = 单板增加 × 计划生产数量
  │
  ├─ 【优先级量化】
  │   └─ 紧急指针 = f(生效窗口, 单板涨幅, 库存, 替代可达性)
  │   └─ 按紧急指针排序输出处理清单
  │
  └─ 【趋势量化】（连续观测）
      └─ 近7天/30天/90天价格变化趋势图
      └─ 预测下月可能的再调幅度
```

交期风险量化同理：`单板延期风险 = max(命中物料的交期天数) - 项目计划排产提前期`。

## 5. 关键设计决策

### 5.1 为何按"来源权威性"而非"内容可信度"定置信度权重

数据源的权威性比单次抽取的匹配度更稳定。一个原厂官网公告即使字段不完整，也比 KOL 写得再详细更值得信。权重排布：来源 30% + 字段 35%，保证权威来源优先自动生效。

### 5.2 为何设置 80 / 50 两个阈值

- 80 分是"可以放心自动处理"的分界线。Mouser 返回 EOL（95）、三源交叉验证（85）不需要人再看。
- 50 分是"足以触发分析"的底线。低于 50 分的信息不足以撼动 BOM 风险评估，留着备查即可。
- 50-79 之间的模糊地带交给人工，且 1 小时超时自动降级，避免"等人处理导致风险遗漏"。

### 5.3 为何哨兵是三组而非一组

价格、库存、生命周期的数据源和变化频率完全不同：

- 价格和库存是每天（甚至每小时）变化的数值，需高频对比。
- 生命周期是低频但高风险的二元状态变化，需定期全量扫描。
- 拆成三组哨兵可以独立调度，互不阻塞。

## 7. 新旧方案对比

| 维度 | v1.1 | v2.0 |
|------|------|------|
| 数据源 | LCSC + Mouser + 用户上传，合计 3-5 个 | 九大类 20+ 渠道全覆盖 |

## 8. 实施优先级调整

鉴于 v2.0 的改动范围较大，分三步走：

**第一步（本周，1-3天）**：置信度分流 + 现有数据源增强
- MarketEvent 上置信度字段。
- 实现自动分流逻辑。
